# PM Working Plan: Jarvis Core/Add-on Modularization → v0.8.0

> Granular companion to the canonical epic doc
> [docs/changes/v0.8.0-modularization-epic.md](../../../docs/changes/v0.8.0-modularization-epic.md).
> The epic doc is the reviewable source of truth; this file holds PM's step-level
> "Done when" criteria + verification strategy. If they diverge, the epic doc wins.

Split the monolithic `enthali.jarvis` extension into a kind-agnostic **session
engine** (core) + optional **PIM** and **Recorder** add-ons, via an IoC plugin
registry proven by the research spike. Ships as **one v0.8.0 release** bundling
the 3 already-merged CRs on develop + the whole split.

## Locked decisions (user, 2026-06-17)
- **Release:** bundle everything into **v0.8.0** (no intermediate v0.7.1).
- **Repo:** **monorepo** with npm workspaces; one `docs/` spec tree; lockstep versioning.
- **Git:** per-CR feature branches off develop, squash-merged. develop stays
  releasable through Phase A/B (one extension, behaviour unchanged).
- Core keeps id **`enthali.jarvis`** → monolith updates in-place into core.
- Namespacing from day one: `jarvis_*` (core) / `jarvis_pim_*` / `jarvis_rec_*`.
- `JarvisCoreApi.version` present from day one.
- `context.md` is NOT an engine concern (session/agent owns it).
- Tree factory is task-agnostic; PIM decorates its own kinds.
- Marketplace/Open-VSX channel decision is DEFERRED to a separate later CR.

## PHASE A — Engine API contract (Step 1)

### CR A1 — Freeze `JarvisCoreApi` v1 + register `session` internally
- Define `JarvisCoreApi` types (§4 of report): `version`, `registerEntityKind`,
  `registerTool`, `registerScheduledJob`, `findEntity`/`createEntity`/`openEntity`,
  `scanner`, `sendToSession`. Plus `EntityKindConfig`.
- Thin internal impl wired to EXISTING code; `activate()` returns the API object.
- Register the `session` kind through `registerEntityKind` INTERNALLY (reference app,
  proves the hook in-tree before pim/recorder use it).
- New spec: `docs/design/spec_engine.rst`. Traceability US/REQ/SPEC for the engine contract.
- Ground the API shape in the spike's proven `SpikeEngineApi` (registerEntityKind +
  registerTool + duplicate-rejection + generic tree provider).
- **Done when:** compiles, activate() returns API, session still works identically,
  existing 44 tests green, engine spec added. No behaviour change.

## PHASE B — Internal modular cut along future seams (Step 2)
Still ONE extension. Behaviour unchanged. Each CR test-green before merge.
Target layout: `src/{extension.ts(composition root), engine/, apps/session/,
apps/pim/, apps/recorder/, shared/}`. Module boundaries = future extension seams.

### CR B1 — Module skeleton: shared/ + engine/ (pure moves)
- Move to `shared/`: logging, templates (`applyTemplate`), `yamlString`, `toKebabCase`,
  `findLeafNode`, `flattenLeaves`.
- Move to `engine/`: `yamlScanner`, `configPaths`, `mcpServer`, `sessionLookup`,
  `messageQueue`, `heartbeat` (scheduling hook `registerScheduledJob`), `registerTool`
  (from `registerDualTool`). extension.ts imports from them.
- **Done when:** behaviour identical, all commands/tools/views work, tests green.

### CR B2 — Extract apps/recorder/ (most self-contained; report says recorder first)
- Move `recording.ts` (`RecordingManager`), transcript-watcher job, start/stop commands,
  `jarvis.recording.*` settings into `apps/recorder/`.
- Recorder consumes engine hooks: `registerScheduledJob` (transcript watcher) + kind hook
  for recording commands (attach via engine's contextValue contract, not hard-coded kinds).
- Ride-along F6: swap 2-min polling for `createFileSystemWatcher('**/output/*.txt')`.
- **Done when:** recording works on session/project/event identically, tests green.

### CR B3 — Generic tree-provider factory (F2)
- Collapse `projectTreeProvider` + `eventTreeProvider` + `sessionTreeProvider` into one
  engine `TreeProvider<K>` factory + per-kind config (label formatter: date vs plain;
  contextValue; optional filters).
- Factory has ZERO task specifics (task children/badges become PIM decoration in B5).
- **Done when:** all three trees render identically (incl. event date-sort, future filter),
  tests green.

### CR B4 — Unify entity create/find/open → `createEntity` (F5)
- Collapse `createProjectEntity`/`createEventEntity`/`createSession` into engine
  `createEntity(kindConfig, args)`; `findEntity`/`openEntity` per §4.
- Create tools become generic kind-dispatch over createEntity.
- `openEntity` owns the agent-mode prime + init-prompt template (collapses F3 delays + F4 to one place).
- **Done when:** newProject/newEvent/newSession/newEntity + create tools behave identically, tests green.

### CR B5 — Extract apps/pim/ (largest payload)
- Move `src/pim/*`, `src/outlookIntegration/*`, project+event app configs (kind registration
  for project/event), `jarvis_category`/`jarvis_task`/`jarvis_listProjects`/`_listEvents`/
  `_createProject`/`_createEvent` tools, categories/tasks tree+editor, project/event
  filter/search commands, `jarvis.projects.*`/`events.*`/`pim.*`/`outlook.*` settings handling.
- PIM decorates project/event kinds with task children/badges (the B3 factory stays task-agnostic).
- Outlook category auto-create on project/event creation becomes PIM-internal (layered on createEntity).
- **Done when:** projects/events/categories/tasks/outlook all behave identically, tests green.
- **Open:** may split into B5a (project/event apps + their tools/trees) and B5b
  (categories/tasks/outlook) depending on B3/B4 diff size.

### CR B6 — Extract apps/session/ + thin composition root
- Move session reference app to `apps/session/`. Reduce `extension.ts` to
  activate()/deactivate() + composition root (~150 lines).
- **Done when:** extension.ts is thin wiring, everything behaves identically, tests green.

## PHASE C — Physical split + package manager (Step 3)
Monorepo (npm workspaces). Emits 4 .vsix. This is where packaging changes.
GATE: verify R9 (`workbench.extensions.uninstallExtension` with a real id in a
controlled env) BEFORE CR C5.

### CR C1 — Monorepo scaffolding + jarvis-core package
- Introduce npm workspaces; `packages/core` (id stays `enthali.jarvis`) = engine + apps/session.
- core build emits `jarvis-<ver>.vsix`. Verify in-place update from monolith id.
- **Done when:** core .vsix installs/updates in place, sessions work, zero project/event in core manifest.

### CR C2 — jarvis-pim as separate extension
- `packages/pim` (`enthali.jarvis-pim`), own `contributes.views`+`configuration`,
  `extensionDependencies: ["enthali.jarvis"]`, calls engine API in activate().
- **Done when:** core-only install shows PROVABLY zero project/event surface (view/setting/command/schema);
  installing pim lights up project/event + PIM features.

### CR C3 — jarvis-recorder as separate extension
- `packages/recorder` (`enthali.jarvis-recorder`), depends on core, hooks any kind.
- **Done when:** core+recorder (no pim) records into a session; core+pim+recorder records into any kind.

### CR C4 — Extension Pack + 4-vsix build
- `packages/suite` (`enthali.jarvis-suite`) = extensionPack of the 3 ids. Build emits 4 .vsix.
- Pack is inert for local installs (no registry); becomes one-click once a gallery exists.
- **Done when:** CI emits 4 .vsix; pack manifest lists the 3 ids.

### CR C5 — Self-updater → package manager (depends on R9 gate)
- Generalize `updateCheck.ts`: probe installed members, update only opted-in ones,
  single reloadWindow(). Lockstep version assets named `<id>-<ver>.vsix`.
- Cutover UX: settings-seeded add-on offer (detect projects/events/recording/outlook enabled →
  offer to install pim/recorder); add via installExtension(fileUri), remove via uninstallExtension.
- **Done when:** core-only updates core only; settings-seeded offer installs add-ons; spike #6/#7 behaviours hold.

### Release — v0.8.0
- `syspilot.release` bundles the 3 pre-existing develop CRs + the whole split.
- Release notes: split overview + cutover guidance (core-only sheds code; PM-project clicks "Install add-ons").
- Lockstep version across all 4 packages.
