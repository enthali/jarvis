- **Actual**: The previously reported High heartbeat gap (queue-only behavior) matches ADR-12 and is not an implementation defect; the former recommendation to add sender-side activation is superseded. The actual preference violation was the reminder poller's prior `addAutoDelivery` call. `d5b392c` removes that call and routes through a helper that only invokes `appendMessage` ([extension.ts](../../packages/core/src/extension.ts#L1612), [reminderDelivery.ts](../../packages/core/src/apps/session/reminderDelivery.ts#L4)). The timer callback itself was not executed in a VS Code host.
- **Scheduling, removal, and legacy queue**: The fix changes only the reminder poll callback's enqueue operation. It still calls `popDueReminders` before enqueueing; `addReminder`, `removeReminder`, and due-item removal in the reminder store are unchanged ([reminders.ts](../../packages/core/src/apps/session/reminders.ts#L26), [reminders.ts](../../packages/core/src/apps/session/reminders.ts#L60), [reminders.ts](../../packages/core/src/apps/session/reminders.ts#L68), [extension.ts](../../packages/core/src/extension.ts#L1602)). `enqueueReminder` delegates to the existing `appendMessage`, preserving its current/legacy queue union and migration behavior; the current reminder-runtime, reminder-policy, and legacy-queue focused selection passes 19/19. ### Issue 6: Persistence-write failure may not retain due reminders

- **Severity**: Medium verification gap / potential contract deviation. **Category**: Code / Test.
- **Expected**: `REQ_MSG_REMINDERS_DELIVER` AC-6 requires reminder-processing errors to be caught and warned without stopping the loop ([req_msg.rst](../requirements/req_msg.rst#L1003)); `REQ_MSG_REMINDERS_PERSIST` AC-6 requires atomic removal of due reminders ([req_msg.rst](../requirements/req_msg.rst#L971)). The focused L2-cleared contract recorded in the Change Document says a `popDueReminders` persistence failure returns an empty result for only the current tick, leaves due reminders persisted for a later retry, and performs no enqueue or refresh on that failed tick ([Change Document](one-kind-consolidation.md#L321)).
- **Actual**: `processDueReminders` now catches a thrown `popDueReminders`, warns, and returns `[]` before enqueue or reload ([reminderDelivery.ts](../../packages/core/src/apps/session/reminderDelivery.ts#L20)). The test verifies those effects and a later successful retry, but its injected function throws before invoking the real pop/write implementation ([reminder-runtime.test.ts](../../src/tests/reminder-runtime.test.ts#L143)). The real `writeReminders` writes directly to the target with `fs.writeFileSync` and has no temp-file replacement or rollback ([reminders.ts](../../packages/core/src/apps/session/reminders.ts#L36)); therefore retention after a write error that occurs after truncation or a partial write is not established. Existing `popDueReminders` still removes/persists due entries before the append attempt, preserving the successful at-most-once ordering ([reminders.ts](../../packages/core/src/apps/session/reminders.ts#L68), [reminderDelivery.ts](../../packages/core/src/apps/session/reminderDelivery.ts#L30)).
- **Recommendation**: Do not treat the injected throw test as proof of real persistence-failure retention. The owner should either provide evidence that the storage operation preserves the old file on write failure or make the write atomic and test failure/retry behavior; retain removal-before-enqueue semantics for successful pops. This report does not change implementation or requirements, and does not claim broad L2 approval, QM OK, or User UAT.
