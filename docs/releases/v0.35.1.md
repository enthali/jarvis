## Objective And Scope

**Owner:** Project Manager<br>
**Status:** approved

### Objective

Pre-release 0.35.1 (`Channel: pre-release`, tag `v0.35.1-pre`) migrates `.github/workflows/release.yml` from `VSCE_PAT` to VS Code Marketplace OIDC Trusted Publishing (`@vscode/vsce` `4.1.1`), adds the tag-driven `pre-release` channel (`vX.Y.Z-pre`, `--pre-release` on package and publish for all six Marketplace extensions, `prerelease: true` on GitHub Release) together with pre-release-aware Release Notes URL lookup in `releaseNotes.ts` and user opt-in instructions in Getting Started, splits `.github/workflows/docs.yml` into `build` and `deploy` jobs on Node-24 actions, fixes retired `enthali.jarvis` references in `packages/mcp/README.md`, and streamlines all 68 User Stories to three personas without leaked internal API names. Publishing on the `pre-release` channel verifies OIDC Trusted Publishing, Marketplace Pre-Release channel isolation, and the two-job GitHub Pages workflow live without pushing an infrastructure-focused release to stable users. The version number is Release's SemVer decision; the Project Manager's candidate is `0.35.1` (plain `0.35.1` in manifests, tagged `v0.35.1-pre`).

## Publication

**Owner:** Release<br>
**Status:** pending | published

Publish only when Release Verification is `proceed` and Open Findings is `None`.

1. Archive the included Change Contracts with `git mv` to `docs/changes/v{version}/` and commit the release preparation on `development`.
2. Bring local `main` up to `origin/main`, squash-merge `development` into `main`, and commit.
3. Tag `v{version}` for the release channel or `v{version}-pre` for the pre-release channel, as the Contract's `Channel` says, and push `main` and the tag. The tag is irreversible, so check its spelling against the Contract before pushing.
4. Watch `release.yml` on the tag and `docs.yml` on `main` to completion. Verify the GitHub Release lists every extension and is marked Pre-release if and only if the tag ends in `-pre`, the Marketplace shows the new version (as a pre-release for a `-pre` tag), and the Pages deployment succeeded. A failed `deploy` job of `docs.yml` is re-run on its own; a failed `build` job is a finding.
5. Close every GitHub issue in `Related GitHub Issue(s)` with `Shipped in v{version}.`
6. Merge `main` back into `development` and push `development`.
